# 渲染器只做呈现，不介入内容

## Status

accepted

## 决定

第一版渲染器**不改变文档的信息密度**：不生成摘要、不做分层提炼、不删减冗余、不重写措辞。它只负责排版、导航与图表呈现。密度问题交回作者。

## 为什么

调研里最有力的一条反驳来自 Hacker News 的高质量评论：AI 文档读不下去的根因常常是**啰嗦**（信息密度低），不是格式。"换格式解决不了低信息密度。"如果渲染器顺手做摘要，就等于让阅读面与真源在**语义**上分叉——读者看到的是渲染器改写过的版本，而 agent 读到的是原始 markdown，同一份文档的两个表示开始说不同的话，这直接违反 ADR-0001 的双表示同源前提。

## Considered Options

- **渲染时自动生成 TL;DR / 分层摘要**：看起来最对症，但制造"读者版 ≠ agent 版"的语义分叉，且摘要质量随模型漂移、无法被 diff 评审。拒绝。
- **渲染时自动裁剪"冗余"段落**：作者无法预期自己的内容被删，破坏信任。拒绝。
- **给出密度提示（例如标记超长章节）**：只提示、不修改，仍符合本 ADR 的精神，可后续加入。

## Consequences

- 想提升可读性，正确做法是改真源，而不是让工具代劳。文档里"这一节太长"应该由作者拆，不由渲染器猜。
- 密度问题仍是真实痛点，只是被明确移出本项目第一版范围；若日后要处理，须先解决"读者版与 agent 版不同源"的问题，那将是新的 ADR。
- 人因测试（定位埋点所需时间）必须在渲染器可用后做，用来验证"只换呈现、不改内容"是否真的提升了阅读效率——如果证明不能，本 ADR 需要重开。

## 人因测试记录

第一条数据来自 `test/human/`（同一问题，MD 纯文本 vs HTML 阅读面，8 题 × 2 条件，N=1）：

| 条件 | 中位耗时 | 平均 | 正确率 |
| --- | ---: | ---: | ---: |
| MD 纯文本 | 24.1s | 31.0s | 7/8 |
| HTML 阅读面 | 15.6s | 20.1s | 7/8 |

中位比 `MD/HTML = 1.55×`（HTML 快 35%），配对胜负 HTML 6 : 2 MD。按预注册标准（≤0.8 支持、≥1.0 触发重开），**数值落在支持区间**。

**但这一轮不作数**：条件顺序是「前 8 题全 MD、后 8 题全 HTML」，条件与时间完全共线，学习效应被整块记到 HTML 上。装置已修为交替编排，需要重跑一轮才能作为确认。

因此本 ADR 的状态**暂不变更**：方向一致、幅度未经确认。

第二轮（交替编排，消除了条件顺序混淆）：

| 轮次 | 有效 | MD 中位 | HTML 中位 | 比值 |
| --- | --- | ---: | ---: | ---: |
| subject-01 | 否（顺序共线） | 24.1s | 15.6s | 1.55× |
| subject-02 | 是 | 25.7s | 26.3s | **0.98×** |

**结论：0.98× 落在预注册的"不确定"区间。第一轮的 35% 优势没有复现，主要是练习效应。** 剔除唯一一道两轮皆错的歧义题后比值回到 1.24×，但那是事后剔除，只能当线索。

三条可以确定的事：

1. **正确率在两种条件下始终相同**（7/8，错的还是同一题）——换呈现不改善理解质量；
2. 题间跨度（42s / 46s）远大于条件中位差（约 1s）——决定耗时的是题目难度，不是呈现形式；
3. 重跑同一套题有记忆污染（`registry` 在 MD 条件从 20.1s 降到 9.0s），要坐实必须换人或换题。

对 ADR-0003 本身的影响：**决定不变**（渲染器依然不改写内容），但"只换呈现能提升阅读效率"这个**附带的效率主张降级为未证实**。对外只主张可验证的能力（单文件转发、离线打开、导航与锚点、同源 `.md` 出口），不以"读得更快"作为卖点。

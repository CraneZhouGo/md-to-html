# 人因测试：同一问题，两种阅读条件

ADR-0003 里写了一条**自我失效条款**：「人因测试若证明'只换呈现'没提升效率，这条 ADR 必须重开」。这个目录就是执行它的地方。

## 在测什么

**定位耗时**：给定一个需要跨章节查找的问题，从题目出现到提交答案用了多久。

不测：阅读速度、理解深度、主观偏好。这些用这个装置测不出来，装作能测会得出假结论。

## 两个条件

| 条件 | 是什么 | 怎么生成 |
| --- | --- | --- |
| `md` | 原始 markdown 纯文本（等宽、无目录、无样式） | 直接把真源转成 `<pre>`，模拟在编辑器里读原文 |
| `html` | 渲染后的单文件阅读面 | 用渲染器产出，**被测的就是用户实际会拿到的产物** |

`md` 条件刻意保持"能用"：它是真实的阅读方式之一，不是稻草人。区别只在于有没有导航、排版、锚点、表格渲染。

## 题库

`tasks.mjs` 里 8 道题，全部来自真实文档 `examples/Java服务架构演进与部署实践总结.md`，每题满足：

1. 答案唯一且短（数字或组件名）——可机械校验，不受表述差异干扰；
2. 要搜的是"问到的东西"而不是答案串本身；
3. 分布在不同章节，逼出定位行为而不是从头读。

每题跑两个条件 → 16 试次。**两个条件各自独立洗牌**（固定种子 20261030，可复现），所以不会出现"所有 MD 题都在前"或"所有 HTML 题都在后"。

## 预注册的判定标准（跑之前写下，避免事后解释）

对此：**HTML 中位耗时 / MD 中位耗时**

| 比值 | 结论 |
| --- | --- |
| ≤ 0.8 | 支持"只换呈现确有收益"，ADR-0003 成立 |
| 0.8 – 1.0 | 不确定：方向对但幅度不足以支撑主张 |
| ≥ 1.0 | **触发 ADR-0003 的自我失效条款**：只换呈现没带来可测收益，需要重开决策 |

正确率单独看：若某条件下正确率明显更低（例如跳过更多），则"更快"没有意义。

## 怎么跑

```bash
npm run human:build      # 生成 out/human/{harness,doc-md,doc-html}.html
npm run human:serve      # 起本地服务并打开浏览器（只监听 127.0.0.1:7788）
#   做 16 题 → 页面下方「下载结果 JSON」→ 放进 test/human/results/
npm run human:analyze    # 输出中位数、正确率、配对比较
```

**必须用 `human:serve`（http）而不是双击 `file://`**：`file://` 下 iframe 是跨源，拿不到 `contentWindow`，每题就无法把文档滚回顶部——那会让"上次读到哪"混进测量结果。

## 必须遵守的约束

- **不许用 Ctrl+F。** 整个实验测的是"文档能不能被扫读定位"，用了查找就变成测打字速度。
- **不许切窗口查资料。** 找不到就点「跳过」，跳过也是有效数据。
- 一次做完 16 题。中途停下会让学习效应和疲劳混在一起。

## 第一轮发现的方法缺陷（已修）

第一轮（`results/subject-01.json`）的条件顺序是**前 8 题全 MD、后 8 题全 HTML**——因为生成计划的循环是「一个条件跑完再跑下一个」，所谓"各自洗牌"只随机了条件**内部**的顺序，没随机条件**之间**的位置。后果：

- 条件与时间完全共线，**学习效应与热身效果全被记到 HTML 头上**；
- 这一轮的中位比 `MD/HTML = 1.55×`（HTML 快 35%）因此**不能作为确认**，只能算"方向一致"。

修法：两个条件各自洗牌后**交替编排**（起点随种子随机）。上面"怎么跑"一节的描述现在与实现一致。第二轮应当用修好的版本重跑，作为不受顺序污染的比较。

同时修正一处题面歧义：`registry` 题原先问"镜像仓库的组件叫什么"，而文档里 `Docker镜像` 与 `Harbor` 相邻，两种条件都答成了 `docker`。已改为"构建好的镜像推送到哪个组件"，指向唯一答案。

## 两轮结果与判定

| 轮次 | 有效 | MD 中位 | HTML 中位 | 比值 MD/HTML | 正确率 |
| --- | --- | ---: | ---: | ---: | --- |
| subject-01 | 否（顺序共线） | 24.1s | 15.6s | 1.55× | 7/8 / 7/8 |
| subject-02 | 是（交替编排） | 25.7s | 26.3s | **0.98×** | 7/8 / 7/8 |

按预注册标准，**0.98× 落在"不确定"区间**（≤0.8 支持、≥1.0 触发重开）。也就是说：

- 第一轮那个"HTML 快 35%"**没有复现**，它主要是条件顺序造成的练习效应——这正好证明"把条件与时间解耦"是必要的；
- 敏感性分析：剔掉唯一一道两轮皆错、题面有歧义的 `registry` 后，比值变成 **1.24×**（HTML 快 24%）。但这是**事后剔除**，只能当线索，不能当证据；
- 正确率在两种条件下**始终相同**（7/8，错的还是同一题）——**换呈现没有带来理解质量上的收益，只有可能的速度收益**；
- 题间跨度（MD 42.3s、HTML 46.1s）远大于条件差（中位差约 1s）——**决定耗时的是题目难度，不是呈现形式**。

## 重跑同一套题本身也有代价

第二轮换了顺序，但没有换题：同一份文档、同一批题、同一个人。第二轮里 `registry` 在 MD 条件下从 20.1s 掉到 9.0s，这种量级的下降只能来自"上一轮见过"。所以第二轮也只是**部分干净**：顺序混淆消除了，记忆污染没有。

要真正坐实，需要的是**换人**或**换文档换题**，而不是再跑一遍。

## 对产品主张的影响

这台装置测出来的唯一稳的结论是：**"换成 HTML 让人读得更快"这个主张没被证实**。

因此对外的主张应当改成能力性的、可验证的：

- ✅ HTML 可以单文件转发、离线打开（可验证）
- ✅ 导航/目录/锚点让"跳过不读"成为可能（可验证）
- ✅ 同一真源同时给出 `.md` 给 agent（可验证）
- ❌ 读得更快（本实验未能证实，不应写进卖点）

## 已知局限（写在这里，不用等人来指出）

- **N=1**（自测）。样本量为 1 时，任何差异都可能是个体偏好，不足以宣称普适结论。
- **学习效应**：同一题在两种条件下各出现一次，第二次必然更快。两个条件独立洗牌只能均衡而不能消除这一点——所以配对差值的**绝对值**不可信，**方向和量级**才有参考价值。
- **题目-条件耦合**：8 道题无法覆盖所有内容类型；若某类内容（如大表格）恰好都落在 HTML 条件的题上，会放大它的优势。
- **装置本身有成本**：右侧面板、输入框、计时器都会分散注意力，两种条件同样受害，但不是零。
- 没有对照组（例如"用 mermaid 渲染的 HTML"或"用别人写的 PDF"），所以结论只适用于本项目的这两个产物。

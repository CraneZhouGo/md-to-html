    HTML 会不会取代 Markdown？

    这场讨论真实存在，有明确起点、有产品落地，但它的主张范围比传闻窄得多：换掉的是给人的那一层，不是真源。

    文档类型
    技术调研
    证据强度
    7 组实证 + 反方章节
    结论
    MD 为真源，HTML 为阅读面

    被推翻的三个前提

    第一，「用 HTML 替代 MD」确实存在，但只在一层成立。第二个前提——「AI 生成的 markdown 动辄数千行」——没有任何一手信源支持；可考的最大量级是 400 行、1,800 词、5k tokens。第三个前提被最硬的数据直接反驳：「HTML 更适合 LLM」并不成立。

    i
    先说结论
    换掉的只是「给人的那一层」。所有严肃信源都同时保留 markdown 作为真源：给 agent 读的、要 diff 的、要协作编辑的，继续用 markdown。

    注意第二行的三个数字：HTML 是 2.23，纯 Markdown 是 1.42，而「Markdown 加一份索引地图」是 0.11。差别不在标记语言，在有没有地图。

    The most surprising find was that markdown itself wasn't the fix, the map was. Plain markdown was arguably the worst of the four formats.

    成本差在「谁写 HTML」

    让模型直接吐 HTML，成本是 markdown 的靠近两倍；而「模型只写 markdown 草稿、由确定性渲染器出 HTML」，成本是手写 HTML 的约八分之一。这条决定了实现形态：

    def render(md: str, profile: Profile | None = None) -> str:
    """确定性渲染：同一输入 + 无偏好 = 逐字节相同的输出。"""
    doc = parse(md)                 # 只解析，不改写文字
    doc = visualize(doc, rules=STRICT)   # 图形化：条件不满足则原样保留
    html = layout(doc, toc=static_toc(doc))  # 目录在构建期生成，静态写入
    return inject_theme(html, profile) or html

    尚未确定
    无偏好时的哈希断言、以及 --profile 的 JSON schema 版本号，要等渲染器写出来才能钉死。

    对本仓库的含义

    1. 真源永远是 markdown；HTML 是可丢弃、可重建的阅读面。
    2. 不做打印样式——需要纸面稿的人应该拿原始 markdown，页面给出口即可。
    3. 承重件是导航，不是配色：目录、锚点、索引。
    4. 图形化只在机械条件全部满足时启用；画错的图不会被 diff 审查发现。
